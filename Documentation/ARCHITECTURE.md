# Architecture and data contract

## Recommended stack

- **Frontend:** React + TypeScript, built with Vite. The creator route owns the plan workspace; the full-screen viewer route owns panorama navigation and an owner-only Edit mode for links. Both use the shared tour domain model. Firebase Authentication handles sign-in.
- **Panorama renderer:** Photo Sphere Viewer v5 behind `PanoramaAdapter`; see [research](VIEWER_RESEARCH.md). Keep our graph and orientation math independent of its plugin types.
- **Backend:** Express + TypeScript JSON API. Firebase Admin verifies ID tokens, and services enforce tour ownership. Route handlers call domain services; services use a SQLite repository and an S3 storage adapter.
- **Object storage:** private S3 bucket (or S3-compatible service in local development) for original panoramas, plan images, and generated thumbnails. Browsers upload to short-lived signed URLs issued by Express.
- **Database:** SQLite for tours, pages, scenes, placements, connections, link overrides, and media metadata. Enable foreign keys, use migrations and WAL mode, and commit graph changes in transactions.

```mermaid
flowchart LR
  E[React creator] --> F[Firebase Authentication]
  V[React viewer] --> F
  E -- Bearer ID token --> A[Express API]
  V -- Bearer ID token --> A
  A -- verify ID token --> F
  A --> D[(SQLite)]
  A --> S[(S3 bucket)]
  E -- signed upload --> S
  V -- signed media read --> S
  A --> W[Image verification and thumbnail step]
  W --> S
  W --> D
```

SQLite is appropriate for an initial single-deployment app with modest simultaneous writes. Its database file must live on persistent storage and be backed up together with the S3 objects. If multiple API instances or high write concurrency become necessary, replace the repository implementation and migrate to a server database; the React app and API shapes should not depend on SQLite details.

## Reusable code boundaries

```text
apps/
  web/
    src/app/                 routes and app shell
    src/auth/                Firebase client, session, and protected routes
    src/features/tours/      tour loading and commands
    src/features/editor/     library, canvas, pages, inspector
    src/features/viewer/     full-screen viewer, thumbnail tray, owner link editing
  api/
    src/auth/                Firebase Admin verification and owner checks
    src/routes/              HTTP parsing and response mapping
    src/services/            tour, graph, media, and manifest rules
    src/repositories/        SQLite queries and migrations
    src/storage/             S3 signing and object verification
    src/jobs/                image validation and thumbnails
packages/
  domain/                    shared types, validation shapes, bearing math
  panorama/                  PSV adapter and React lifecycle wrapper
  ui/                        local theme tokens and shared controls
Documentation/
```

The editor canvas owns page transforms, selection, dragging, and graph visuals. The viewer owns panorama link handles and its owner-only Edit mode; there is no embedded panorama preview in the editor. The panorama adapter owns only rendering and direction conversion. The backend service layer enforces graph invariants and access control; the frontend may mirror them for immediate feedback but cannot be the sole validator. See the [authentication contract](AUTH.md).

## Domain model

| Record | Main fields | Rules |
| --- | --- | --- |
| `tours` | `id`, `owner_uid`, `title`, `entry_scene_id?`, `default_north_yaw_deg`, `version`, timestamps | `owner_uid` is the verified Firebase UID. One tour owns all pages and scenes. `default_north_yaw_deg` is the photo-local yaw where north appears under the shared capture assumption. The entry scene must belong to the tour. |
| `media_assets` | `id`, `tour_id`, `kind` (`panorama`/`plan`), `object_key`, `thumbnail_key?`, `underlay_page_id?`, original filename, normalized filename key, MIME, dimensions, byte size, `status`, error code, retirement time, timestamps | Object keys are generated by the server. An underlay upload belongs to one page. A pending replacement does not displace the current ready image. Only ready panoramas become viewable scenes. |
| `scenes` | `id`, `tour_id`, `panorama_asset_id`, `name`, `sort_order`, `north_yaw_override_deg?` | One scene per current ready panorama asset. The optional override has the same photo-local meaning as the tour default. Every scene is in the viewer tray, with or without a placement. |
| `pages` | `id`, `tour_id`, `name`, `sort_order`, `north_angle_deg`, `plan_asset_id?`, underlay frame/transform | A tour always has at least one page; its raster underlay is optional and belongs only to that page. North defaults to page up. The underlay frame is part of the page world, not the viewport background. |
| `placements` | `id`, `tour_id`, `page_id`, `scene_id`, `x`, `y` | A scene has at most one placement in the initial build. Coordinates are in stable logical page units, independent of pan/zoom and image pixels. |
| `plan_connections` | `id`, `tour_id`, `placement_a_id`, `placement_b_id` | Unordered relationship between two placements. Same-page connections draw a solid line; cross-page ones draw portal indicators. |
| `navigation_links` | `id`, `tour_id`, `source_scene_id`, `target_scene_id`, `plan_connection_id?`, `position_mode` (`auto`/`manual`), `manual_yaw_deg?`, `manual_pitch_deg?` | Directed hotspot. `plan_connection_id = null` means it was created in the panorama viewer and has no full canvas connection. |

Constraints enforced by services and database migrations:

- Each referenced page, asset, scene, and placement belongs to the same tour. A link cannot target its own source scene.
- At most one **plan connection** exists for an unordered pair of placed nodes. It owns at most one directed link in each direction. Viewer-created links have their own IDs and may repeat the same directed source/target pair, including a pair already connected on the canvas. Migration 4 removed the directed source/target uniqueness constraint and added uniqueness only for a plan connection's source direction; link selection uses link IDs.
- A same-page plan connection creates two directed links by default. Existing viewer-created links remain independent, with their custom positions unchanged. The two plan-owned link positions can diverge afterward.
- `auto` is valid only for a link owned by a same-page plan connection. Its manual yaw/pitch fields are null. `manual` requires both angles. Cross-page and unplaced-scene links are manual.
- Removing a placement deletes its plan connections and the links belonging to those connections. Independent links with `plan_connection_id = null` remain. Removing a scene deletes its placement and every link to or from that scene.
- Removing a page is rejected when it is the tour's last page. Otherwise, a transaction removes its placements, all plan connections touching those placements (including cross-page ones), and their attached links before removing the page. Its underlay asset is retired for storage cleanup. Scenes and independent viewer-created links remain.
- Do not rely on database cascading alone for user-visible delete behavior; return a preview/count for confirmation and perform the final mutation transactionally.

If a creator removes one direction of a plan connection, retain the connection and show its remaining direction on the canvas. Removing the connection itself removes its attached link directions. This supports one-way navigation without changing the two-way default.

## Coordinate and orientation rules

Store page positions in a stable logical page coordinate system, for example a 1000 × 1000 plane with `x` increasing right and `y` increasing down. Render the page underlay as an image element in that world alongside node markers and connection paths. A single viewport transform pans and zooms the whole world; do not use a viewport-fixed CSS background for the underlay. Invert that transform to convert a click into page coordinates before creating or moving a node. The underlay has a stable page-space frame; replacing or removing its image does not change stored node coordinates. In the first canvas slice, lock independent underlay movement and resizing after placement. If underlay transforms become editable later, anchor nodes to image-local coordinates or transform them together so their registration is preserved.

The canvas editor has one active interaction state: selected library photo, selected node, create-link source, or idle. Every ready library photo is selectable; choosing a placed photo switches to its page and highlights its node, while choosing an unplaced photo arms canvas placement. A successful placement clears the photo selection. Clicking a node loads its plan connections and independent viewer links into the inspector. **Create Link** arms that node as source; clicking a different node on the same page creates one unordered plan connection unless that pair is already connected. A separate page/target picker handles cross-page connections. Deleting a ready photo is an owner-scoped transaction that removes its scene, placement, plan connections, and links before retiring its assets; a running replacement upload must finish or be canceled first. The editor and viewer share the numbered photo card renderer and scene-number function. The viewer link editor has its own library selection state, clears it after one hotspot is placed, and disables only the current source photo to prevent a self-link.

For two placements on the same page:

```text
dx = target.x - source.x
dy = target.y - source.y
canvasBearingDeg = atan2(dx, -dy) × 180 / π   // clockwise from page up
headingDeg = normalize360(canvasBearingDeg - page.northAngleDeg)
autoPitchDeg = 0
```

The reverse link uses the bearing from the other node, so its heading differs by 180°. A zero-length connection is invalid because its direction is undefined. `northAngleDeg` is the clockwise angle from page up to the north arrow. Thus a target directly right is east only when north points up.

The viewer manifest maps heading to photo-local yaw as `normalize360(sourceNorthYawDeg + headingDeg)`, where `sourceNorthYawDeg` comes from the scene override or the tour default. PSV receives that photo-local yaw directly. The tour-level calibration covers the initial shared-camera-direction assumption; an optional per-scene override handles images with different seams or metadata. Four cardinal calculation fixtures pass, but the sign and visible image orientation still require a browser pass with representative photos. Do not scatter sign flips across components.

Store manually adjusted yaw/pitch in **photo-local spherical coordinates** (`yaw` normalized modulo 360, `pitch` from -90 to +90). The adapter passes those angles to PSV as degrees and converts pointer coordinates back to angles when a handle is dragged. This keeps a custom hotspot attached to the same part of a photo if north calibration changes. An auto link resolves its direction from current placements whenever the graph is read or mutated. A manual link resolves solely from its saved angles, so moving nodes never overwrites it. “Reset to plan” will switch a same-page, placed link back to `auto` and clear the manual fields.

## API outline

All endpoints below are under `/api`. Every endpoint requires a verified Firebase ID token and server-side tour-owner check, except creation and listing, which use the verified UID directly. Request and response shapes live in `packages/domain` and are validated on the server. IDs in route paths are scoped to the tour. Use atomic commands for connection creation/deletion because they affect multiple link rows.

| Endpoint | Purpose |
| --- | --- |
| `GET /tours` | List tours whose `owner_uid` matches the verified Firebase UID. |
| `POST /tours`, `GET /tours/:id`, `PATCH /tours/:id` | Create/load/edit a tour, including entry scene and orientation calibration. `GET` returns an editor aggregate. |
| `POST /tours/:id/uploads` | Reserve an asset and return a short-lived signed S3 upload URL. |
| `POST /tours/:id/uploads/:assetId/complete` | Verify the uploaded object, validate the image, generate a thumbnail, and return the ready scene or an error. Processing currently runs in the request. |
| `DELETE /tours/:id/uploads/:assetId` | Cancel a pending or failed upload and clean up its object. |
| `GET /tours/:id/assets/:assetId/thumbnail-url`, `GET /tours/:id/assets/:assetId/read-url` | Return short-lived signed GET URLs for a ready scene's thumbnail or original. |
| `POST /tours/:id/pages`, `PATCH /tours/:id/pages/:pageId`, `DELETE /tours/:id/pages/:pageId` | Manage floors and north direction. Delete takes `expectedVersion`, rejects the last page, removes its nodes/plan links, and retires its underlay. |
| `POST /tours/:id/pages/:pageId/underlay/uploads`, `POST /tours/:id/pages/:pageId/underlay/uploads/:assetId/complete` | Sign an upload for a raster underlay and attach it only after validation. A replacement keeps the prior underlay visible until completion. |
| `DELETE /tours/:id/pages/:pageId/underlay/uploads/:assetId` | Cancel and clean up an incomplete or failed underlay upload. |
| `GET /tours/:id/pages/:pageId/underlay-url`, `DELETE /tours/:id/pages/:pageId/underlay` | Sign a private read URL; or clear the page's underlay, retire its stored image, and retain nodes and links. |
| `PATCH /tours/:id/scenes/:sceneId`, `DELETE /tours/:id/scenes/:sceneId` | Rename/reorder or explicitly delete a photo scene. |
| `POST /tours/:id/placements`, `PATCH /tours/:id/placements/:id`, `DELETE /tours/:id/placements/:id` | Place, move, or unplace a scene. |
| `POST /tours/:id/connections`, `DELETE /tours/:id/connections/:id` | Create/remove a unique plan connection for a pair of nodes and its directed links transactionally. Reject a duplicate pair. |
| `POST /tours/:id/links`, `PATCH /tours/:id/links/:id`, `DELETE /tours/:id/links/:id` | Create a viewer-origin link, including another hotspot to an existing destination; set a custom angle; remove an independent link by ID. Reset-to-plan is planned. |
| `GET /tours/:id/viewer-manifest` | Read-only scenes, resolved links, page labels, thumbnails, entry scene, and short-lived media URLs. |

The viewer manifest includes every **ready** scene, ordered by placed page/scene order and then unplaced upload order. Each link is emitted with a resolved `{ yaw, pitch }` and destination scene ID. The browser sends no S3 credentials to the API. Signed GET URLs have an expiry in the manifest; refresh them before they expire during a long viewing session. Configure S3 CORS for the frontend origin so WebGL can load textures. Treat creator-supplied names as plain text; sanitize any content passed to a PSV caption or tooltip that accepts HTML, as its [configuration guide warns](https://photo-sphere-viewer.js.org/guide/config).

The first build can have one editor at a time. Include a tour `version` with editor mutations so stale writes return a conflict instead of silently overwriting another session. The app can then refetch and show a conflict state.

Underlay upload, replacement, and removal are page-scoped owner-authorized mutations. Accept JPEG, PNG, or WebP raster images, verify content and size before attaching, and store them as `plan` media assets. The small **×** beside the top-right underlay upload/replace link removes the page reference first, then deletes the retired S3 object through retryable cleanup. An underlay replacement uses the same commit-and-cleanup order. Nodes and plan links are independent of the underlay asset lifecycle.

## Upload and media lifecycle

1. Express checks the declared MIME type and size against configured limits, creates a random object key, and signs a short-lived PUT URL. The browser sends the original directly to S3 with the signed `Content-Type`. The photo library accepts several files at once and serializes uploads with the same normalized name.
2. The browser calls `complete`. The API checks the stored object's size and MIME type, reads it, validates a JPEG/PNG/WebP image with a roughly 2:1 aspect ratio and minimum 1024 × 512 dimensions, generates a JPEG thumbnail, and marks the asset ready or failed. Processing currently runs inline in the completion request. Its SQLite state lets a later request retry after an interruption.
3. A new name creates a scene. A matching name within the tour, case and extension insensitive, switches the existing scene to the validated asset in one transaction. The scene ID, title, order, placement, and links are retained. The old ready image stays active until that transaction commits; a failed upload does not replace it.
4. The editor aggregate includes current assets and their statuses. The library shows local transfer progress, ready thumbnails, and interrupted or failed uploads. A pending or failed upload can be checked again or canceled. Canceled and replaced S3 objects are cleaned up after the database change; retired rows allow cleanup to be retried on startup.
5. The API signs read URLs for originals and thumbnails only for current ready scenes. Do not serve a pending panorama in the viewer manifest. Explicit scene deletion and its graph cleanup remain a later editor step.

Start with conventional full-sphere equirectangular still photos (roughly 2:1) and raster plan images. Camera metadata can affect crop and heading, so preserve original metadata and test representative exports. Later, a tiling pipeline can be added behind the media adapter for very large panoramas; PSV has an [equirectangular tiles adapter](https://photo-sphere-viewer.js.org/guide/adapters/equirectangular-tiles.html).

## Access and deployment boundary

Firebase Authentication is the chosen identity provider. Both creator mode and the initial viewer require the owner to sign in. Express verifies the Firebase ID token, uses its UID to authorize every tour and media operation, and assigns `owner_uid` on tour creation. The client does not choose the owner. Viewer Edit mode is only a client affordance; link mutations are authorized by the same owner check as other editor mutations. Public share links can later authorize only the viewer manifest and media reads, never edit controls or mutations. Avoid making the S3 bucket public by default. See [authentication and tour access](AUTH.md) for flows and checks.

Deploy the React build as static assets and Express as a persistent service with a durable SQLite volume. Store Firebase Admin and S3 credentials only on the API. Back up SQLite consistently and retain S3 media with a matching retention policy. Log upload failures and manifest errors with tour/asset IDs rather than tokens, media URLs, or credentials.
